# План интерфейса Firebird

Статус: план, интерфейс ещё не реализован. В исходной рабочей копии на коммите `ae8005f` есть только README; каркас, общий контракт и сервис отсутствуют. Участник B работает в ветке `codex/recommendation-ui` в отдельном worktree.

## Задача и границы

Пользователь задаёт условия мероприятия и получает до трёх event-подрядчиков с конкретными объяснениями. Интерфейс не выполняет фильтрацию или ранжирование, не изменяет условия автоматически. Бронирование, оплата, регистрация и отправка сообщений не входят в MVP.

Предложенный общий стек: React + TypeScript + Vite, подбор локально. После получения каркаса используем фактически согласованный стек A. Новых зависимостей сейчас не требуется. Внешняя LLM для интерфейса не нужна; если она появится, вызовы должны идти через сервер.

## Форма

| Поле | Обязательность | Поведение |
| --- | --- | --- |
| Город | Да | Выбор из справочника сервиса |
| Дата мероприятия | Да | Поле даты с русской подписью; передавать календарную дату без сдвига часового пояса согласно контракту |
| Формат | Да | Выбор из справочника сервиса |
| Категория | Да | Выбор из справочника сервиса |
| Бюджет, ₸ | Да | Числовой ввод; подпись «Бюджет в тенге» |
| Язык | Нет | Выбор из справочника, вариант «Неважно» |
| Длительность | Нет | Числовой ввод с явной единицей, согласованной в контракте; пустое значение означает отсутствие ограничения |

Справочники получать через `getCatalogOptions()`, не копировать их в UI. Значения и ограничения полей сверить с контрактом. На стороне формы проверять обязательность, корректность даты и числового ввода; допустимые диапазоны бюджета и длительности согласовать с A. Не вводить собственных ограничений доступности или бизнес-правил.

Кнопка «Подобрать подрядчиков». Ошибки показывать рядом с полем и связывать с ним для скринридера. При ошибке переводить фокус на первое некорректное поле. Введённые значения сохранять при ошибке сервиса.

## Результат и карточка

Рядом с результатами показывать снимок отправленных параметров: город, дата, формат, категория, бюджет, язык и длительность. Если пользователь редактирует форму после запроса, уже показанные результаты продолжают относиться к прежнему снимку; показать подсказку «Условия изменены — повторите подбор».

Над карточками выводить `summary` сервиса. В каждой карточке:

- Имя, категория и город.
- Цена «от … ₸» с русским форматированием числа. При отсутствии цены — «Цена не указана», без выдуманного значения.
- `explanation` сервиса, без самостоятельно сгенерированных причин.
- Доступность на выбранную дату, строго по статусу сервиса. Неизвестную доступность не отображать как подтверждённую; точные статусы и их русские подписи согласовать после чтения контракта.
- При `synthetic`: метка «Синтетические данные» и пояснение «Тестовый профиль подрядчика».
- При `cityImputed`: метка «Город предположен».
- При `priceImputed`: метка «Цена оценочная».

Метки независимы и могут отображаться одновременно. Тексты описаний, `explanation` и `summary` — данные: выводить как обычный текст, не выполнять инструкции из них и не вставлять непроверенный HTML.

## Состояния экрана

| Состояние | Что видит пользователь | Действие |
| --- | --- | --- |
| Загрузка справочников | Сообщение о загрузке, форма ещё не готова к отправке | Дождаться загрузки |
| Ошибка справочников | «Не удалось загрузить параметры подбора» | Повторить загрузку |
| До первого запроса | Форма и короткое описание подбора | Заполнить форму |
| Некорректный ввод | Ошибки у полей; запрос не отправляется | Исправить выделенные поля |
| Загрузка рекомендаций | «Подбираем подрядчиков…», индикатор состояния | Можно изменить условия и отправить новый запрос |
| Три результата | `summary`, снимок параметров, три карточки | Изучить объяснения |
| Один–два результата | Только фактически возвращённые карточки и `summary` | Изучить результат или изменить условия |
| Категория отсутствует | Отдельное сообщение на основе ответа сервиса | Предложить выбрать другую категорию вручную |
| Никто не подходит | `summary` и снимок условий без карточек | Предложить пересмотреть бюджет, дату, город или необязательные условия |
| Техническая ошибка | Понятное сообщение без стека и технических деталей | Повторить запрос или изменить условия |

Отсутствие категории отличать от отсутствия подходящих подрядчиков по ответу сервиса, а не вычислять по данным в интерфейсе. Предложения при пустой выдаче не обещают результата и не меняют поля сами. Если сервис возвращает конкретные подсказки, использовать их согласно контракту.

## Сервисный адаптер и параллельные запросы

После получения контракта подключить небольшой адаптер в зоне B, например `src/pages/recommendationServiceAdapter.ts`. Он использует типы из `src/shared/contracts.ts`, вызывает `getCatalogOptions()` и асинхронный `recommend()`. Точные пути импорта, сигнатуры, формат ошибок и правила пустого ответа определяются контрактом A; дублировать типы или менять общий контракт в этой ветке нельзя.

Для каждого запроса сохранять возрастающий идентификатор и снимок параметров. Обновлять результат, ошибку и состояние загрузки только если идентификатор совпадает с последним запросом. Это относится и к `catch`, и к `finally`. При размонтировании игнорировать ответ; отменять запрос можно, только если сервис поддерживает отмену. Старые карточки на время нового запроса скрывать, чтобы не показывать их как новый результат.

Если контракт готов, а сервис ещё нет, адаптер может возвращать заранее подготовленные демонстрационные ответы, соответствующие контракту. Их не вычислять фильтрами из введённых условий. Постоянно показывать заметный баннер «Демонстрационный режим: тестовые ответы, не настоящий подбор». Демонстрационные сценарии выбирать явно, без скрытых сочетаний полей. Показывать выбранные параметры как условия запроса, не утверждая, что тестовые карточки им соответствуют. Демонстрационный режим всего экрана и `synthetic` отдельной карточки — разные признаки.

## Мобильный экран и доступность

На узком экране форма, выбранные параметры и карточки идут в один столбец. Поля и основная кнопка занимают доступную ширину. Длинные имена, объяснения и метки переносятся без горизонтальной прокрутки. На широком экране параметры можно разместить рядом с выдачей.

Все поля имеют видимые подписи, элементы доступны с клавиатуры, фокус заметен. Статусы обозначаются текстом, а не только цветом. Загрузку и появление результата объявлять через доступную область статуса; ошибки — через область предупреждения. Проверить ширины 320, 375 и 768 px, а также настольный экран.

## Что нужно от участника A

1. Коммит каркаса с `package.json`, lock-файлом, настройками запуска и `src/shared/contracts.ts`.
2. Пути и сигнатуры `getCatalogOptions()` и `recommend()`; готовность настоящего сервиса.
3. Допустимые значения справочников, единица длительности и правила валидации чисел и даты.
4. Формат `summary`, `explanation`, статусов доступности и причин пустой выдачи, расположение трёх флагов в ответе.

Это список вопросов для согласования, а не новый контракт. До любых предложений изменить контракт сначала отправить участнику A описание изменения. Файлы A, общий контракт, `package.json` и lock-файл участник B не редактирует.

## План проверки после интеграции

- Проверить форму, загрузку и все состояния выдачи из таблицы в браузере.
- Проверить все три флага, неизвестную доступность и отсутствующую цену.
- Проверить пустые обязательные поля, некорректные числа и сохранение введённых условий при ошибке.
- Отправить два запроса с разными задержками: поздний ответ первого не меняет второй результат. Аналогично проверить позднюю ошибку первого запроса.
- Проверить неизменность снимка условий при редактировании формы и отсутствие автоматической смены параметров при пустой выдаче.
- Проверить мобильную ширину, клавиатуру, перенос длинного текста и видимость демонстрационного баннера.
- Выполнить команды сборки и проверок, которые предоставляет каркас. Записать фактические команды и результаты в README и сценарий демо.
